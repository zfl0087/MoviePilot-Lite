# MoviePilot Lite 上游同步与发布

## 1. 文档目的

本文档规定 MoviePilot Lite 持续跟踪 MoviePilot 官方稳定版本时使用的远程仓库、分支、同步、测试、候选验证、正式发布和回退流程。

同步流程必须同时满足以下目标：

- 保留官方提交历史和版本可追溯性。
- 控制 Lite 补丁规模及长期冲突成本。
- 防止官方新增能力绕过 Lite 能力门控进入运行时。
- 自动完成可重复的候选构建和测试，但保留正式发布及生产升级的人工批准。
- 任何失败均不得影响当前稳定运行实例。

具体产品范围以根目录 `PROJECT_BRIEF.md` 为准，架构门控以 `docs/ARCHITECTURE.md` 为准。

## 2. 远程仓库

### 2.1 后端

| 远程 | 地址 | 权限 |
|---|---|---|
| `origin` | `https://github.com/zfl0087/MoviePilot-Lite.git` | 私有 Lite 仓库，可推送 |
| `upstream` | `https://github.com/jxxghp/MoviePilot.git` | 官方仓库，只读 |

### 2.2 前端

| 远程 | 地址 | 权限 |
|---|---|---|
| `origin` | `https://github.com/zfl0087/MoviePilot-Lite-Frontend.git` | 私有 Lite 仓库，可推送 |
| `upstream` | `https://github.com/jxxghp/MoviePilot-Frontend.git` | 官方仓库，只读 |

### 2.3 插件

官方插件仓库 `jxxghp/MoviePilot-Plugins` 单独跟踪，不把其源码合入 Lite 核心仓库。P115StrmHelper 由用户通过插件市场手动安装，Lite 只维护兼容约束和验收记录。

`upstream` 必须保持禁止推送。任何脚本、自动化或人工操作都不得向官方仓库写入分支、标签、Release 或其他内容。

## 3. 分支模型

| 分支 | 生命周期 | 用途 |
|---|---|---|
| `upstream/v2` | 长期只读 | 官方稳定开发基线 |
| `lite` | 长期 | Lite 日常集成和下一候选版本 |
| `main` | 首次正式版时创建 | 已通过真实验证的稳定版本 |
| `sync/v<官方版本>` | 临时 | 单次官方版本同步和冲突处理 |
| `change/<openspec-id>` | 临时 | 单项 Lite 变更实现 |

分支规则：

- 不向私有仓库额外推送 `v2` 镜像分支，避免与 Lite 产品分支混淆。
- 不直接在 `lite` 或 `main` 上处理大型同步冲突。
- 不对 `lite` 或 `main` 强制推送。
- `main` 只接收已经通过候选测试和 Canary 验证的内容。
- 临时分支完成合并并确认不再需要后，才可按单独审批流程删除。

## 4. 稳定版本判定

官方后端版本只有同时满足以下条件时，才进入 Lite 同步流程：

1. 目标提交已经进入官方 `v2`。
2. 官方 `version.py` 已声明新的 `APP_VERSION`。
3. 官方存在与该版本匹配的非预发布标签或正式 Release。
4. `FRONTEND_VERSION` 能匹配一个明确的官方前端版本。

只出现分支提交、Beta 构建或预发布标签时，不自动进入 Lite 稳定同步。

每次同步必须记录官方后端和前端的完整提交哈希，不能只记录分支名或浮动的 `latest`。

## 5. 同步流程

```mermaid
flowchart LR
    A["发现官方稳定版本"] --> B["创建 sync/v版本"]
    B --> C["合并 upstream/v2"]
    C --> D["匹配对应前端版本"]
    D --> E["冲突与能力边界审查"]
    E --> F["后端、前端和集成测试"]
    F --> G["构建私有候选镜像"]
    G --> H["Canary 真实验证"]
    H --> I["用户批准"]
    I --> J["合入 main 并发布固定版本"]
```

标准步骤：

1. 只读检查官方新版本、Release 说明及后端和前端提交。
2. 从当前 `lite` 创建 `sync/v<官方版本>` 临时分支。
3. 使用合并方式引入 `upstream/v2`，不得通过变基改写官方或 Lite 历史。
4. 根据官方后端 `FRONTEND_VERSION` 选择对应前端基线，并在前端创建同版本同步分支。
5. 审查冲突、依赖变化、数据库迁移、新增路由、模块、任务和后台服务。
6. 重新验证 Lite 能力门控及插件兼容性。
7. 分别通过后端、前端和集成测试。
8. 合入 `lite` 并构建固定提交对应的候选镜像。
9. 在 Canary 实例完成真实115工作流验证。
10. 获得用户明确批准后，将同一候选内容推进到 `main` 并发布正式版本。

同步过程中任何阶段失败，都必须停止后续发布，不得自动降级测试范围或忽略失败。

## 6. 合并策略

- 上游同步使用合并提交，保留官方提交的祖先关系。
- Lite 单项变更应保持小范围、单一目的，并关联对应 OpenSpec。
- 不得通过整文件选择 Lite 版本或官方版本的方式掩盖冲突，启动、路由、模块加载、依赖和数据迁移文件尤其需要逐项审查。
- 同步分支不得包含与本次上游版本无关的功能开发。
- Lite 适配提交应与上游合并提交分开，便于后续审计和撤销。

## 7. 冲突处理规则

| 冲突类型 | 处理规则 |
|---|---|
| Lite 保留功能 | 优先吸收官方修复，再适配 Lite 能力门控 |
| Lite 已移除功能 | 可保留上游源码历史，但不得恢复注册、依赖和运行链路 |
| 启动、路由、模块加载 | 必须人工逐项审查，不得直接选择一侧覆盖 |
| 数据库迁移 | 原则上保留官方迁移，维持 `/config` 和官方回退兼容 |
| 依赖文件 | 逐项判断 Lite 是否需要，不得直接复制官方完整依赖集 |
| 前端路由和菜单 | 由统一能力清单决定，不得恢复已移除页面 |
| 插件接口 | 验证保留插件框架及 P115StrmHelper，不得为其他插件恢复已移除核心 |
| 消息权限 | 保留官方身份和权限语义，只裁剪不支持的命令动作 |

官方新增的 API、模块、后台服务、定时任务、消息动作或依赖默认视为未启用，只有完成产品分类、能力声明和测试后才可进入 Lite。

## 8. 数据库与配置同步

- 不主动删除官方数据库迁移，即使迁移涉及 Lite 不再运行的能力。
- Lite 专属数据库迁移必须保持最少，并明确验证官方版本回退影响。
- 不删除已移除模块留下的配置项、历史数据和未知字段。
- 同步后必须使用官方兼容 `/config` 副本完成升级测试。
- 任何可能改变数据库结构的候选版本，在 Canary 启动前必须创建数据库和关键配置备份。

## 9. 前后端版本配对

后端和前端作为一个候选版本共同验证，但保留两个独立源码仓库。

每个候选版本必须固定：

- 官方后端版本和提交。
- 官方前端版本和提交。
- Lite 后端提交。
- Lite 前端提交。
- Lite 能力配置版本。

后端 `FRONTEND_VERSION` 必须指向明确的 Lite 前端版本或构建产物。禁止从浮动分支、`latest` 或未记录提交的临时产物构建正式镜像。

## 10. 版本格式

| 类型 | 格式 | 示例 |
|---|---|---|
| 正式版 | `v<官方版本>-lite.<修订号>` | `v2.14.5-lite.1` |
| 同一官方版本后续修订 | 递增 Lite 修订号 | `v2.14.5-lite.2` |
| 候选版 | 正式版后追加 RC 号 | `v2.14.5-lite.1-rc.1` |

版本号不得复用。已经发布的标签、Release 和镜像标签不得删除后重新指向其他提交。

## 11. 自动化启用阶段

### 11.1 项目初期

- 上游检查、同步和候选构建只允许手动触发。
- 每次触发前按 `AGENTS.md` 获得用户明确批准。
- 先验证权限、测试、镜像命名和回退流程，不立即启用定时任务。

### 11.2 流程稳定后

在多次人工同步成功并经用户单独批准后，可以启用定时检查和自动候选构建。自动化最多执行到候选镜像及报告阶段。

自动化永远不得：

- 自动合入 `main`。
- 自动发布正式版。
- 自动升级家庭生产实例。
- 自动覆盖已有标签、Release 或镜像。
- 把真实115令牌或生产配置注入普通 CI。
- 在测试失败或冲突未解决时继续发布。

## 12. 测试门禁

候选版本至少通过以下检查：

### 12.1 后端

- 完整 pytest 测试。
- Pylint 检查。
- 运行依赖安全扫描。
- SQLite 初始化、升级、备份和回退测试。
- 能力关闭模块的未导入、未注册、未实例化和未调度测试。
- 保留 API、消息通知、插件和媒体服务器接口回归测试。

### 12.2 前端

- TypeScript 类型检查。
- 单元测试。
- 生产构建。
- 未启用页面不进入路由和构建产物的检查。
- 与后端能力配置版本一致性检查。
- 插件 remote 缺失和加载失败不得阻止核心启动，且 P115StrmHelper 等插件源码不得进入核心 bundle。

前端候选报告必须记录测试数量、覆盖率结果、转换模块数、PWA 预缓存项数、产物文件数及总字节数。当前未提交工作树的参考结果为：56 个 Lite 测试（statements/lines 96.78%、branches 83.57%、functions 100%），1964 个转换模块，187 个预缓存项，184 个产物文件、9,972,540 字节；正式候选必须在提交后重新生成，不能复用该临时结果。

### 12.3 镜像与集成

- Docker `linux/amd64` 和 `linux/arm64` 构建。
- 使用模拟服务验证启动、登录、网盘、整理、通知、插件和媒体服务器流程。
- 检查镜像中不存在已移除能力的专属依赖和资源。
- 与相同官方版本比较内存、镜像体积和冷启动时间。

普通 CI 不得连接真实 TMDB、115、消息渠道、媒体服务器或其他生产服务。真实验证只在隔离 Canary 实例执行。

## 13. Canary 验证

候选镜像必须在非生产 Canary 实例至少完成一次：

- 使用备份后的兼容 `/config` 启动。
- 管理员登录。
- 115 授权和文件访问。
- 消息渠道接收115分享链接。
- P115StrmHelper 转存。
- 元数据识别、文件整理和 STRM 更新。
- 通知回传。
- Emby、Jellyfin 或 Plex 刷新。
- 重启、异常恢复和升级失败回退。

Canary 使用的真实令牌只保存在实例安全配置中，不写入仓库、构建日志、测试产物或 GitHub Actions Secrets。

## 14. 私有镜像与发布

- 初期只使用与私有仓库关联的私有 GHCR，不使用 Docker Hub。
- 不发布或部署浮动的 `latest`。
- 候选和正式镜像均使用完整版本标签。
- 生产 Compose 固定具体版本，建议同时记录镜像摘要。
- 正式 Release 必须标明非官方 MoviePilot Lite 私有构建，并保留 GPLv3、版权和修改说明。
- 向可信对象分发镜像时，同时提供该镜像对应的完整源码和版本追溯信息。

官方现有构建工作流会针对 `v2` 发布 `latest`、使用 Docker Hub并删除后重建 Release，因此不得原样作为 Lite 发布流程。Lite 工作流必须单独设计、审查和批准。

## 15. 发布记录

每个候选和正式版本至少记录：

- 官方后端完整提交哈希。
- 官方前端完整提交哈希。
- Lite 后端完整提交哈希。
- Lite 前端完整提交哈希。
- 能力配置版本。
- 依赖清单和测试结果。
- Docker 平台、标签及镜像摘要。
- Canary 验证时间和结果。
- 数据库备份位置及回退验证结果。

## 16. 回退流程

生产升级前必须备份 `/config` 和 SQLite 数据库。出现问题时：

1. 停止失败的新版本实例。
2. 保存失败版本日志、提交号、配置版本和镜像摘要。
3. 部署上一个已验证的固定镜像版本。
4. 如果数据库或配置发生不兼容变化，恢复升级前备份。
5. 验证登录、网盘、插件、消息通知、整理和媒体服务器刷新。
6. 为失败版本建立修复 OpenSpec，不在生产实例直接试改。

回退操作不得依赖已被覆盖的标签或浮动镜像。
