## Why

Lite 的运行时能力、前端门禁和 Docker 内容合同已经分别完成，但当前仍没有一条能把固定后端提交与固定前端提交组成同一候选的受控构建路径。现有 Dockerfile 默认按 `version.py` 下载官方前端 Release；这只能证明版本号，不能证明镜像包含私有前端 `lite` 分支的固定提交。

本变更建立可审计的候选构建流程，解决三个风险：前后端错配、单架构通过后被误当成完整候选、构建凭据或产物意外公开。候选构建成功不等于可发布，也不替代真实 115 Canary。

## What Changes

- 新增手动触发的私有候选工作流，显式接收后端 SHA、前端 SHA 和候选版本标签。
- 在工作流中从私有前端仓库检出固定 SHA，完成前端类型检查、Lite 测试、覆盖率、生产构建和产物扫描。
- 修改 Docker 构建接口，使候选镜像消费已验证的前端构建目录或不可变归档，而不是重新下载浮动前端 Release。
- 使用 Buildx 同时构建 `linux/amd64` 与 `linux/arm64`，生成不可变候选标签、镜像摘要、提交配对清单和资源/门禁报告。
- 在推送 GHCR 前执行镜像内容合同、物理缺失检查、干净容器启动/停止和保留功能的模拟验证。
- 将 GHCR 推送、候选环境和权限边界设为独立批准点；本变更不部署 Canary、不发布正式版本。

## Non-Goals

- 不改变 Lite capability profile、PT 认证移除、网盘/整理/插件/通知功能边界。
- 不自动同步上游、不创建公开 Fork、不向 `upstream` 推送。
- 不把真实 115、P115StrmHelper、消息渠道或媒体服务器凭据放入 GitHub Actions。
- 不创建 `latest`、Docker Hub 或公开 GitHub Release。
- 不在当前 Windows 主机上假装完成 Linux 双架构构建或资源指标验收。

## Impact

- 后端：新增候选构建工作流、构建辅助脚本和对应合同测试；Dockerfile 接受已验证前端产物。
- 前端：工作流只读取指定 SHA 并生成候选产物，不修改前端源码。
- GitHub：需要私有前后端仓库读取权限、GHCR 包写入权限，以及候选发布环境的人工审批配置。
- 运维：候选镜像仅供后续隔离 Canary 使用；正式升级仍需另行批准。
