## Context

MoviePilot 当前没有贯穿后端、前端和构建流程的能力定义。`app/api/apiv1.py` 静态导入全部端点，`app/startup/modules_initializer.py` 在初始化前导入站点、Redis、Agent 等服务，`ModuleManager` 也会先导入扫描到的模块再判断其运行设置。直接在这些入口分别维护 Lite 排除清单会导致定义漂移，并可能在判断发生前触发非目标依赖或副作用。

本变更先建立纯数据、无业务依赖的 Lite 能力配置。它是后续门控工作的基础，但本身不接入任何运行入口，因此不会让“清单中禁用”被误解为“已经完成裁剪”。详细产品边界以 `PROJECT_BRIEF.md` 为准，门控原则以 `docs/ARCHITECTURE.md` 为准。

## Goals / Non-Goals

**Goals:**

- 在 `app/core/capability.py` 建立唯一、固定且可测试的 Lite 能力分类。
- 提供不可变启用集合、派生禁用集合和严格的能力查询函数。
- 提供带版本的确定性机器可读清单，作为后续前端与 Docker 构建输入的源数据。
- 保证该模块可在任何业务模块之前安全导入，不触发配置、数据库、插件或外部服务。
- 通过测试锁定当前已批准的能力边界，防止上游同步时静默扩大 Lite 范围。

**Non-Goals:**

- 不修改 API 路由、启动生命周期、模块扫描、定时任务、消息命令或插件加载。
- 不修改前端仓库，不生成前端构建产物。
- 不删除 Python、Node 或 Docker 依赖。
- 不引入运行时 Lite/完整版切换，也不提供环境变量覆盖。
- 不验证真实 115、消息渠道或媒体服务器流程。
- 不在本变更中宣称实现资源占用下降。

## Decisions

### 1. 使用独立的纯 Python 核心模块

新增 `app/core/capability.py`，只允许导入 Python 标准库中的枚举和类型工具。该模块不读取 `settings`、环境变量、`/config` 或数据库，也不导入 `app.api`、`app.chain`、`app.modules`、插件管理器和外部 SDK。

选择这一方案是因为能力判断必须早于现有业务导入。备选方案是在 `app/core/config.py` 增加设置项，但配置模块会处理大量环境与路径状态，而且运行配置可覆盖的语义与“固定 Lite 构建”冲突，因此不采用。

### 2. 使用字符串枚举和单一启用集合

能力标识使用字符串枚举：Python 成员名使用大写下划线，序列化值使用稳定的 kebab-case。`LITE_CAPABILITIES` 使用 `frozenset[Capability]` 保存唯一启用集合；禁用集合在模块加载时由全部枚举值减去启用集合得到，不维护第二份人工列表。

选择枚举而不是裸字符串，可以在代码审查和类型检查阶段发现拼写错误；选择单一启用集合，可以避免启用、禁用两份列表发生重叠或遗漏。能力分类的任何新增或变更必须通过后续 OpenSpec 变更完成。

### 3. 查询接口严格接收 Capability

提供 `is_capability_enabled(capability: Capability) -> bool`。函数先验证参数确实是 `Capability` 实例，再执行集合查询；字符串、未知值或其他类型均明确失败。

不采用自动把字符串转换为枚举或对未知值返回 `False` 的宽松接口，因为这会掩盖调用方拼写错误，也可能使上游新增能力在没有分类审查的情况下静默进入未知状态。需要处理外部字符串的适配层必须显式执行 `Capability(value)` 并处理异常。

### 4. 固定配置身份并输出快照清单

模块定义固定的 `LITE_PROFILE_NAME = "lite"` 和正整数 `LITE_PROFILE_VERSION`。清单生成函数每次返回新的普通字典，字段固定为 `profile`、`version`、`enabled` 和 `disabled`；两个能力列表均按枚举值排序。

返回新快照使 JSON 序列化简单，同时避免调用方修改结果后污染内部状态。本变更不提交另一份手写 JSON 文件，也不增加 HTTP 端点；后续前端构建变更必须通过生成器从该模块产生输入，不能复制维护第二份能力清单。前后端正式版本仍按 `docs/UPSTREAM_SYNC.md` 记录配对。

### 5. 用契约测试锁定边界和导入纯度

测试覆盖确切能力集合、集合互斥与完备、不可变性、严格类型检查、清单排序和返回值隔离。导入纯度通过静态检查该模块仅使用允许的标准库导入，并在隔离测试进程中导入和调用核心接口验证；测试不得连接真实外部服务。

不通过启动完整 FastAPI 应用验证本变更，因为那会引入当前尚未门控的站点、Redis、Agent 等依赖，既扩大测试范围，也无法证明能力模块自身保持隔离。

### 6. 后续变更按入口逐层接入

本变更归档后，后续门控按独立变更实施：先处理 API 与启动生命周期的导入前门控，再处理模块、命令与插件兼容，最后处理前端和 Docker 依赖裁剪。每个阶段必须验证禁用能力未导入、未注册、未实例化、未调度或未打包，不能仅依据清单状态宣称裁剪完成。

## Risks / Trade-offs

- [能力粒度过粗或过细] → 首版使用已批准的产品边界分类；后续只能通过 OpenSpec 修改枚举和配置版本。
- [清单存在但运行时尚未裁剪，造成完成假象] → 规范和测试明确本变更不接入门控，文档与汇报不得把配置状态表述为实际裁剪结果。
- [后续前端复制能力列表导致漂移] → 只允许从 Python 真相源生成机器清单，并以配置版本校验前后端配对。
- [严格查询接口增加适配代码] → 外部输入在边界层显式转换并处理异常，以换取内部调用的可审计性。
- [上游新增功能没有对应枚举] → 上游同步审查必须先分类新功能；未分类能力默认不得进入 Lite 门控允许集合。
- [能力模块意外引入重依赖] → 通过导入允许列表和隔离进程测试阻止业务依赖进入该模块。

## Migration Plan

1. 新增能力模块和单元测试，不修改任何调用方。
2. 运行能力契约测试及与改动相关的静态检查。
3. 验证现有应用入口没有引用新模块，确认运行行为未改变。
4. 将该变更作为后续 API、启动、模块、前端和构建裁剪的前置规范归档。

本变更不修改数据库、`/config`、环境变量或部署文件，不需要数据备份或迁移。若验证失败，删除新增模块和测试即可回退；该回退不影响现有 MoviePilot 数据与运行配置。

## Open Questions

无。能力集合、固定配置语义、序列化字段和本变更的非目标已经明确，可在批准实施后直接编码。
